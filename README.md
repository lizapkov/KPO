# ВышКат - учёт парка кикшеринга

Консольное приложение на C# для учёта парка «ВышКат» (ДЗ №1 по КПО: SOLID, DI-контейнер, юнит-тесты).

## Что умеет программа

- принимать транспорт в парк только после техосмотра (принят / отклонён, причина отказа выводится);
- ставить на баланс вещи: шлем, док-станция, зарядный шкаф;
- выдавать каждому принятому предмету инвентарный номер `VK-0001`, `VK-0002` и т.д.;
- считать количество единиц и суммарное суточное потребление энергии;
- показывать транспорт для новичков (простота >= 6);
- выводить тип, название и инвентарный номер всей техники и вещей;
- показывать демо всех сценариев.

## Запуск

Нужен .NET SDK 10.

```
dotnet build
dotnet run --project src/HSEKAT              # запуск программы с меню
dotnet run --project src/HSEKAT -- --demo    # запуск программы сразу с демкой
dotnet test                                  # тесты
```

Меню: 
- 1 - добавить транспорт
- 2 - добавить вещь
- 3 - статистика
- 4 - транспорт для новичков
- 5 - все названия и номера
- 6 - демо
- 0 - выход.

## Структура

```
src/HSEKAT/
  Interfaces/   IInventoryItem, IEnergyUser, IServiceCenter
  Models/       Vehicle (Bicycle, Escooter, Ebicycle), Item (Helmet, DockStation, ChargingCabin), InspectionRes
  Services/     Park, ServiceCenter, InventoryNumberGenerator, VehicleCatalog, VehicleType
  ConsoleApp.cs меню, ввод и вывод, демо
  Program.cs    настройка DI-контейнера и запуск
tests/HSEKAT.Tests/   юнит-тесты и FakeServiceCenter
```

## Как устроено

**Интерфейсы.**
`IInventoryItem` - всё, что стоит на балансе в парке (название, тип, инвентарный номер).
`IEnergyUser` - всё, что потребляет энергию (суточный расход).
`IServiceCenter` - техосмотр, провряет транспортные средства через метод `Inspect(Vehicle)` по заданным критериям, возвращает `InspectionRes`.

**Модели.**
`Vehicle` - базовый класс для транспорта (название, простота 1-10, износ, пробег). Данные проверяются в конструкторе, с неверными данными объект не создается. `Bicycle` без энергии, `Escooter` и `Ebicycle` ещё реализуют `IEnergyUser`.
`Item` - базовый класс для вещей. `Helmet` не потребляет энергию, `DockStation` и `ChargingCabin` потребляют (`IEnergyUser`). Вещи техосмотр не проходят.

**Сервисы.**
`Park` хранит принятый транспорт и вещи. Перед добавлением транспорта спрашивает `IServiceCenter`, и только если техосмотр одобрил, выдаёт номер и добавляет. Ещё умеет считать энергию, искать транспорт для новичков и отдавать общий список.
`ServiceCenter` - настоящий техосмотр. Правила: износ <= 50%, пробег <= 3000 км, расход энергии <= 5 кВтч (для тех кто потребляет электричество). Если нарушено несколько правил, в причине выводятся все.
`InventoryNumberGenerator` генерирует номера.
`VehicleCatalog` и `VehicleType` - список видов транспорта, меню строится по нему.

## SOLID

**S.** Каждый класс делает одно: `Park` ведёт учёт, `ServiceCenter` проверяет технику, `InventoryNumberGenerator` выдаёт номера, `ConsoleApp` занимается вводом и выводом.

**O.** Новый вид транспорта добавляется новым классом и одной строкой в `VehicleCatalog`. `Park`, `ServiceCenter` и меню не меняются. Энергия считается через `IEnergyUser`, поэтому `GetTotalEnergy` тоже не нужно менять.

**L.** `Bicycle`, `Escooter`, `Ebicycle` можно подставить везде, где нужен `Vehicle`, а `Helmet`, `DockStation`, `ChargingCabin` - везде, где нужен `Item`. `Park` и `ServiceCenter` работают с ними одинаково.

**I.** Интерфейсы маленькие и разные: `IEnergyUser` отдельно от `IInventoryItem`, поэтому шлему и обычному велосипеду не надо реализовывать расход энергии.

**D.** `Park` зависит от интерфейса `IServiceCenter`, а не от `ServiceCenter`. Конкретный класс подставляется в `Program.cs` через DI-контейнер (`Microsoft.Extensions.DependencyInjection`), а в тестах вместо него подставляется `FakeServiceCenter`.

## DI-контейнер
 
Используется `Microsoft.Extensions.DependencyInjection`, всё настраивается в `Program.cs`:
 
```
services.AddSingleton<IServiceCenter, ServiceCenter>();
services.AddSingleton<InventoryNumberGenerator>();
services.AddSingleton<VehicleCatalog>();
services.AddSingleton<Park>();
services.AddSingleton<ConsoleApp>();
```
 
Контейнер сам создаёт `ConsoleApp` и подставляет всё, что нужно в конструкторы (`ConsoleApp` получает `Park` и `VehicleCatalog`, `Park` получает `IServiceCenter` и `InventoryNumberGenerator`). Вручную через `new` ничего не собирается.
 
Зачем он нужен:
- `Park` не знает, какой именно техосмотр ему дали. Чтобы заменить `ServiceCenter` на другой (или на подставной в тестах), достаточно поменять одну строку регистрации, код `Park` не трогаем.
- Все зависимости видно в одном месте, в `Program.cs`.
- Тесты могут собрать `Park` с подменённым техосмотром, не меняя код программы.
Почему `AddSingleton`: парк должен быть один на всё приложение, иначе транспорт будет теряться между вызовами. Генератор номеров тоже один, иначе номера могут повториться.

## Ответы на вопросы

**Какой принцип применён наиболее явно и где?**
D (инверсия зависимостей). `Park` принимает `IServiceCenter` в конструкторе, настоящий техосмотр регистрируется в `Program.cs`, а в тестах подменяется на `FakeServiceCenter`.

**Какой принцип ограничен / почти нарушен и почему это приемлемо?**
O и D частично. Чтобы добавить вид транспорта, всё равно надо дописать строку в конструктор `VehicleCatalog`, то есть код меняется. Правило для новичков (`MinScoreForNovice = 6`) прописано прямо в `Park`. Также `Park` зависит от конкретного `InventoryNumberGenerator`, а не от интерфейса. Это приемлемо: отдельные интерфейсы для генератора и правила были бы лишним усложнением. Если правил станет больше, их можно вынести в отдельный интерфейс.

**Что сломается / не сломается при расширении?**
- Новый вид транспорта (например, самокат с аккумулятором): новый класс от `Vehicle` + одна строка в `VehicleCatalog`. Если он электрический, добавляем `IEnergyUser`, и энергия посчитается сама. `Park`, `ServiceCenter` не меняются.
- Сотрудники: это отдельный класс, который не реализует `IInventoryItem`, поэтому он не попадёт на баланс и не сломает `Park`.
- Склад запчастей: запчасть можно сделать наследником `Item`, тогда `AddItem` и вывод номеров работают без изменений.

**Какой тест фиксирует решение техосмотра / правило для новичков, как подменяется зависимость?**
- Решение техосмотра: `ParkTests.AddVehicle_ServiceCenterRejects_VehicleNotAdded` (отклонённый транспорт не попадает в парк и не получает номер) и `AddVehicle_ServiceCenterAccepts_VehicleAddedWithNumber`. Правила настоящего техосмотра проверяют `ServiceCenterTests` (граничные значения износа, пробега, энергии и случай трёх нарушений сразу).
- Правило для новичков: `ParkTests.GetVehiclesForNovice_ChecksBoundary` (границы 5 и 6) и `GetVehiclesForNovice_ReturnsOnlySuitableVehicles`.
- Подмена: `FakeServiceCenter` (fake) реализует `IServiceCenter`, отвечает «принять / отклонить» как задано в тесте и считает число вызовов. В `ParkTests` он передаётся прямо в конструктор: `new Park(fakeCenter, new InventoryNumberGenerator())`.
- Подмена через DI-контейнер: `DependencyInjectionTests.Container_UsesFakeServiceCenter`. Там в `ServiceCollection` вместо настоящего техосмотра регистрируется `FakeServiceCenter` (`AddSingleton<IServiceCenter>(fake)`), контейнер сам собирает `Park`, и тест проверяет, что `Park` обратился именно к подменённому техосмотру.

## Тесты

- `ParkTests` - парк с подменённым техосмотром: приём и отказ, номера, новички, энергия, общий список.
- `ServiceCenterTests` - правила техосмотра и граничные значения.
- `VehicleTests` (в `ModelsTests.cs`) - проверка данных в конструкторах, `IEnergyUser` только у электрических.
- `InventoryNumberGeneratorTests` - формат и уникальность номеров.
- `ConsoleAppTests` - меню и ввод, ввод и вывод подменяются заготовленным текстом.
- `DependencyInjectionTests` - DI-контейнер собирает `Park` с подменённым техосмотром.

Покрытие тестами более 70% строк.
